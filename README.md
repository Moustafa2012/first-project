# بوابة شفاء · Shifa Portal

[![CI](https://github.com/Moustafa2012/shifa-portal/actions/workflows/ci.yml/badge.svg)](https://github.com/Moustafa2012/shifa-portal/actions/workflows/ci.yml)

سجل صحي إلكتروني متعدد المرضى. لكل مريض ملف رئيسي واحد تتفرع منه ملفات الأقسام الطبية، مع تتبع زمني للقياسات والتحاليل، ومشاركة آمنة مع الأطباء برابط + PIN.

> المنصة تنظّم المعلومات ولا تشخّص ولا تعالج. التصنيفات (مرتفع/منخفض) مؤشرات فحص عامة للبالغين تستدعي تقييم مختص، وقواعدها مخزنة كبيانات بانتظار مراجعة سريرية (`reviewed_by_clinician = false`).

| **الزيارة والملاحظات** | زيارة الأسنان تسجّل الأسنان والتخدير (نوعه ومادته وكميته) والمواد والمضاعفات والتعليمات المعطاة. الملاحظات تُكتب مسودة ثم تُوقَّع: بعد التوقيع لا يُعدَّل نصها، وأي تغيير لاحق «تعديل موثّق» يُضاف بجانب الأصل مع سببه ووقته وكاتبه؛ وملاحظة الطبيب عبر الرابط موقّعة باسمه ولا يعدّلها غيره. قوالب جاهزة للأسنان (SOAP، حشوة، خلع، عصب، تنظيف، طارئ) وقوالب شخصية من صفحة الحساب. الفحص الدوري (فحص، تنظيف، أشعة، صيانة لثة…) بفترة وموعد يتقدّم تلقائياً عند تسجيل الفحص أو إنجاز العلاج، و«المتابعات المعلّقة» في الملخص وملف الأسنان: المتأخر والقريب، والعلاج الموافَق عليه غير المجدول، والمتابعة التي طلبتها زيارة. |
| **مخطط اللثة** | ست نقاط لكل سن (وحشي-دهليزي، دهليزي، أنسي-دهليزي، ومثلها لسانياً/حنكياً): عمق الجيب وموضع حافة اللثة والنزف والبلاك والقيح، مع الحركة (0–3) وانقسام الجذور بحسب السن (الأرحاء العلوية B/M/D، السفلية B/L، الضاحك العلوي الأول M/D). إدخال سريع: كل رقم يملأ موقعاً وينتقل للتالي. مستوى الارتباط تحسبه القاعدة: CAL = العمق − الحافة (الحافة موجبة فوق ملتقى المينا بالملاط، سالبة عند الانحسار، وصفر إن لم تُقس). المخطط مسودة واحدة تُستكمل لاحقاً، ثم يُعتمد فلا يُعدَّل (يُبطل بسبب فقط)؛ الاعتماد يقدّم موعد صيانة اللثة. ملخص (النزف٪، البلاك٪، الجيوب ≥4 و≥6، متوسط وأقصى الارتباط)، رسم لكل سن، مقارنة مخططين (فقد ارتباط ≥2 مم، تحسّن العمق، الأسنان المفقودة) وPDF. |
| **نظام التصميم** | نظام تصميم Supabase في العمق، بخط «اليمامة»: رموز الألوان منقولة حرفياً من مستودع Supabase (`semantic.css` و`compat.css` وسمتا الفاتح والداكن، بنظام OKLCH) في `src/app/supabase-tokens.css` مع البادئة `--sb-`؛ ومكوّناته مترجمة إلى CSS: Button (primary/default/secondary/outline/dashed/link/text/danger/warning وأحجامه وسطوح التحكم المرفوعة)، وAdmonition بأيقوناته وبنيته (عنوان ثم وصف)، وBadge، وCard برأس وتذييل، وInput/Select/Textarea بحلقة التركيز، وTable، وTabs، وEmptyStatePresentational، وPageHeader، وKeyValue، والشريط الجانبي وقائمة المنتج كما في Studio؛ وتقارير PDF بالألوان نفسها. |
| **التنقل** | غلاف على نمط Supabase: شريط ضيق بأيقونات المنتجات يتسع عند المرور ليُظهر الأسماء، وبجانبه قائمة المنتج النشط بصفحاته (وداخل ملف الأسنان أقسامه نفسها)، وشريط علوي بمسار التنقل ومبدّل سريع بين ملفات المرضى؛ وعلى الجوال زر قائمة يفتح كل المنتجات وشريط أفقي بصفحات المنتج الحالي. المنتجات تتبع رحلة المريض: الملخص، الملف الأساسي، الخط الزمني؛ المتابعة (القياسات، التحاليل، الفحوصات المطلوبة، خطط المتابعة)؛ الأقسام الطبية المستخدمة في الملف أولاً (الأكثر سجلات أولاً) مع «فتح قسم آخر»؛ السجلات العامة؛ المستندات والمشاركة. |
| **الإضافة في مكانها** | في مخطط الأسنان يُختار السن ثم «تشخيص لهذا السن» أو «إجراء» أو «صورة أو أشعة» دون السؤال عن السن أو التخصص. وعند الطبيب عبر الرابط: الملخص السريري أولاً، ثم التعريف والتوقيع مرة واحدة، ثم مساحة القسم (المخطط والإضافة على السن نفسه)، ونموذج الإضافة داخل كل قسم، وفي النهاية ملخص ما أضافه مع إمكان سحب أي إضافة. |
| **ملف الأسنان** | مخطط بانورامي تشريحي (تيجان، وجذور بعددها الصحيح، وقنوات، ولثة وعظم) تُرسم عليه الموجودات في أماكنها: التسوس والحشوات على أسطحها، والتاج، وحشو القناة، والآفة أو الخراج عند الذروة، والزرعة، والمفقود والمطمور، وانحسار اللثة؛ مع عرض «الأسطح» بديلاً. مخطط أسنان تفاعلي SVG بترقيم FDI (دائمة 11–48، لبنية 51–85، ومختلطة)، مرسوم من جهة الطبيب المقابل للمريض في العربية والإنجليزية، بأسطح قابلة للنقر وتحكم كامل بلوحة المفاتيح. فحوص تسجل حالة كل سن (موجود، مفقود، مخلوع، لم يبزغ، مطمور…)، وموجودات على مستوى السطح (تسوس، حشوة، تاج، علاج عصب، زرعة…) مع نوع الإثبات. المخطط الحالي مشتق من التاريخ فلا يُمسح شيء: لوحة لكل سن بتاريخه، والمخطط كما كان بعد أي فحص، ومقارنة فحصين. التشخيصات والإجراءات والأشعة تسمّي أسنانها وتظهر على المخطط (المشكلة النشطة بإطار أحمر ورمزها، وعلامة للإجراء وللصورة) وفي لوحة السن؛ والمشكلات التي لا سن لها بعد تُعرض لتحديد سنها. صفحة واحدة بتبويبات: المخطط والفحوص، المشكلات، الزيارات والإجراءات، الصور، الملف السني. ويسجل طبيب الأسنان فحصاً كاملاً عبر رابط المشاركة. |
| **إضافة الطبيب عبر الرابط** | يختار المريض ما يمكن للطبيب إضافته (زيارة، تشخيص، إجراء، ملاحظة، دواء، موعد، طلب فحص، تصوير، مستند). يحدّد المريض عند إنشاء الرابط اسم الطبيب وتخصصه وعيادته ومدينته (والترخيص والهاتف اختيارياً)، فلا يُدخل الطبيب بياناته بل يؤكد بنقرة أنه الطبيب المذكور ثم يسجّل التشخيص والعمل فقط؛ وتُحفظ كل إضافة باسمه وعيادته داخل نطاق المشاركة، ولا يستطيع تعديل ما سجله المريض. يراجع المريض الإضافات ويبطلها فرادى أو دفعة واحدة، ويسجل التدقيق الطبيب فاعلاً. |

## الأمان (مُنفَّذ في قاعدة البيانات لا في الواجهة)

- **RLS** على كل الجداول؛ الوصول عبر `patient_members` فقط. `anon` بلا أي صلاحية. **المسؤول لا يرى بيانات المرضى.**
- لا `DELETE` على السجلات الطبية؛ `recorded_by/at` تختمها القاعدة؛ لا يمكن للمستخدم رفع «موثق من مصدر معتمد» لنفسه.
- النتيجة المعتمدة لا تُعدَّل في مكانها (مشغّل يمنع ذلك).
- دوال القارئ (`share_open/bundle/document/add_note`) متاحة لـ `service_role` فقط، والجلسة 30 دقيقة، وتُفحص الصلاحية والإلغاء والانتهاء والنطاق **عند كل طلب**.
- رقم الهوية في جدول منفصل، مُقنَّع في الواجهة، ومحجوب من التدقيق والمشاركة.
- رؤوس أمان: Content-Security-Policy للصفحات (المصادر من الموقع نفسه وخطوط Google فقط، `frame-ancestors none`، `object-src none`)، وHSTS، و`nosniff`، و`no-referrer` ومنع التخزين لروابط المشاركة.
- حدود صريحة: لا يمكن منع طبيب من تصوير الشاشة؛ الطباعة والتنزيل ضوابط واجهة.

## التشغيل

```bash
npm install
cp .env.example .env.local     # عبّئ مفاتيح Supabase
# طبّق supabase/migrations/*.sql بالترتيب على مشروعك (supabase db push)
npm run dev
```

متغيرات البيئة: `NEXT_PUBLIC_SUPABASE_URL`، `NEXT_PUBLIC_SUPABASE_ANON_KEY`، `SUPABASE_SERVICE_ROLE_KEY` (خادم فقط: التخزين وبوابة الطبيب)، `NEXT_PUBLIC_SITE_URL`، `SHARE_HASH_SALT` (إلزامي في الإنتاج)، `CRON_SECRET` (لاستدعاء `/api/cron/purge` يومياً لإتمام حذف الملفات بعد مهلة 30 يوماً).

لإنشاء مسؤول: `update public.profiles set role = 'admin' where id = '<user uuid>';`

## الاختبارات

```bash
npm run typecheck && npm run lint
npm test            # 79 اختباراً وحدوياً (السلاسل الزمنية، الرسم، القيم المحسوبة، التواريخ الجزئية، كشف التكرار، ترقيم FDI والمخطط والتشريح البانورامي، السياق السريري، دورة الحالة، خطط العلاج والتكاليف، المتابعات المعلّقة، حسابات اللثة والمقارنة)
npm run test:db     # 541 تأكيد SQL على PostgreSQL 16: العزل، RLS، الحراس، المشاركة وإضافات الطبيب، التدقيق، الحذف، الكتالوج، دقة التاريخ، ملف الأسنان، الملف الأساسي، سجل الحالات، الأقسام المستخدمة، العلاج وخطط العلاج، الزيارة والملاحظات، مخطط اللثة
# اختبار شامل من الطرف إلى الطرف (بلا Docker):
npm run e2e:backend && npm run e2e:app && npm run e2e     # 53 خطوة Playwright
```

تُشغَّل الثلاثة تلقائياً على GitHub Actions مع كل دفع وطلب دمج (`.github/workflows/ci.yml`).

`scripts/dev-backend` **خلفية اختبار محلية** تترجم بروتوكول Supabase (REST/Auth/Storage) إلى SQL فعلي بدور `anon/authenticated/service_role` مع claims الـ JWT، فتكون السياسات والمشغّلات حقيقية. هي ليست PostgREST/GoTrue ولا تُستخدم في الإنتاج. انظر `docs/architecture.md` لحدود ما اختُبر.
